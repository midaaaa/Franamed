# PvP: спецификация бэкенда

Статус: принято (черновик 2 + `forfeitInMs`), реализовано в ветке `pvp/backend`.

## 1. Что строим

Два режима, оба по коду или ссылке. Ни открытых комнат, ни очереди, ни рейтинга.

| | Комната | Дуэль |
|---|---|---|
| Игроков | 2–8 | ровно 2 |
| Цель | больше очков за N фильмов | снять у соперника все HP |
| Длина | хост выбирает 5 / 10 / 15 фильмов | до победы, потолок 20 фильмов |
| Хост | есть: старт, пауза, кик, скрыть ник | нет; матч стартует, когда оба нажали «готов» |
| Вход во время матча | да, со следующего фильма | нет, только в лобби |
| Обрыв | можно вернуться в любой момент | 60 с без сети подряд — техническое поражение |

Тип (фильмы или сериалы) задаёт билет, но допустимые типы ограничивает ключ `pvpMediaTypes`, по умолчанию `"movie"`: сериалов пока 3, и их включат, когда каталог вырастет. Источник — только курируемый рандом: опубликованные тайтлы, у которых одобренных кадров не меньше, чем кадров в раунде, без сегодняшних и будущих фильмов дня. Сначала берутся тайтлы, которых в этой комнате ещё не было. Когда они кончаются, добирается случайно из более давней половины уже сыгранных, как в «Подборке» с перемешиванием (§8). Матч из-за этого не укорачивается. Против одиночной игры не фильтруем: запрос не касается данных игроков. В статистику тайтла и в `watched_media` PvP не пишет.

История матчей на сервере не хранится. Итог со всеми фильмами и кадрами приходит каждому игроку последним сообщением матча, и клиент показывает его один раз. Объект комнаты стирает себя сам.

## 2. Архитектура

```
iPhone ──HTTPS──▶ Worker /v1/pvp/*  ──stub.fetch──▶ Durable Object PvpRoom (один на код комнаты)
       ◀══WebSocket (Hibernation)═══════════════════▶   ├─ core.js  — чистая логика: (state, event, now) → (state, out, alarm)
                                                        └─ хранилище DO: одна запись "state"
                         D1: только pvp_profiles и чтение каталога при старте матча
```

- **Код комнаты** — 6 цифр `0–9`, миллион вариантов: на телефоне его набирают с цифровой клавиатуры. Код и есть имя объекта: `env.PVP_ROOM.idFromName(code)`. Таблица комнат не нужна. Если при создании код занят живой комнатой, воркер тянет другой, до пяти раз. Буквенные коды из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, выданные до перехода на цифры, по-прежнему принимаются, пока такие комнаты не убраны; новые не выдаются. Риск подбора — §14.
- **Ядро** (`src/pvp/core.js`) — чистые функции без Cloudflare. Обвязка (`src/pvp/room.js`) переводит сокеты и alarm в события ядра, сохраняет состояние, рассылает исходящие сообщения и ставит alarm.
- **Таймеры только через alarm.** Ни `setTimeout`, ни `setInterval`: они не дают объекту уснуть. Всегда ставится один alarm — на ближайший из сроков (конец фильма, конец разбора, ожидание готовности, автоснятие паузы, передача хоста, техпоражение, уборка). По alarm ядро получает событие `tick` и закрывает всё, что просрочено.
- **Пинг** — `setWebSocketAutoResponse('{"t":"ping"}' → '{"t":"pong"}')`. Отвечает рантайм, объект не просыпается, это ничего не стоит. Клиент шлёт ping раз в 10 с. При каждом `tick` обвязка смотрит `getWebSocketAutoResponseTimestamp`: сокет без пинга дольше 30 с считается отвалившимся, даже если `close` не пришёл. С DPI так и бывает.
- **Время** — только серверное. Подробности в §5.

## 3. HTTP

Все ручки под `/v1/pvp/`. Кроме `ws` и `poll`, все проходят обычный `authenticate` (access-JWT, `REQUEST_LIMITER`). Ручки `ws` и `poll` принимают заголовок `Authorization: PvP <тикет или resume-токен>`. В адрес токены не кладутся: адреса попадают в логи Cloudflare.

| Метод и путь | Тело → ответ | Что делает |
|---|---|---|
| `GET /profile` | → `PvpProfile` | ник, иконка, цвет. Ник по умолчанию выводится из uid и ничего не пишет |
| `PATCH /profile` | `{name?, icon?, color?, reroll?: true}` → `PvpProfile` | свой ник, 🎲 или аватар. Одна запись в D1 |
| `POST /rooms` | `{kind: "room"\|"duel", mediaType: "movie"\|"tv", films?, frames?, timeLimitSec?}` → `{code, ticket, socketURL}` | создаёт комнату. Настройки берутся из `app_config` и проверяются по допустимым спискам |
| `POST /rooms/{code}/ticket` | → `{ticket, socketURL}` или 404 / 403 / 409 | вход или новое подключение после долгого отсутствия |
| `GET /rooms/{code}/ws?lastSeq=…` | заголовок `Authorization: PvP …` → upgrade в WebSocket | передаётся в объект |
| `POST /rooms/{code}/poll` | заголовок с resume-токеном, `{lastSeq, send: [ClientMessage]}` → `{messages: [ServerMessage]}` | запасной вариант через HTTP (§7) |

Ошибки — в обычном формате `{error, message}`:
- `room_not_found`;
- `room_full`;
- `match_running` (дуэль уже идёт);
- `kicked`;
- `pvp_disabled` (выключатель в `app_config`);
- `media_type_disabled` (тип не входит в `pvpMediaTypes`).

### Тикет

`pvp1.<base64url(payload)>.<mac>`, где `mac = HMAC-SHA256(JWT_SECRET, "pvp-ticket." + payload)`. Используются `hmacBase64Url` и `base64UrlEncode` из `lib/crypto.js`, `lib/auth.js` не трогаю.

Payload: `{uid, code, name, alias, icon, color, exp}`, срок 60 с.

Тикет — это **не** JWT. Префикс `pvp1` не разбирается как заголовок JWT, а MAC считается от другой строки, поэтому `authenticate` его не примет. Профиль вшит в тикет, и объекту не нужно ходить в D1.

Одноразовость: объект помнит `mac` использованных тикетов до их `exp`.

### Resume-токен

При первом подключении объект выдаёт игроку `resumeToken` — 128 случайных бит, действует только в этой комнате и только для этого игрока. Им переподключаются без HTTP-ручки: не тратится запрос к воркеру и D1 и не нужен свежий access-JWT. Токен живёт, пока жива комната.

## 4. Жизненный цикл

```
lobby ──start──▶ loading ──фильмы выбраны──▶ ready(1) ──все готовы / таймаут──▶ countdown ──3 с──▶ playing
  ▲                                              ▲                                                │
  │                                              └────────── reveal(k) ◀── все ответили / дедлайн ┘
  │                                                             │ последний фильм / HP ≤ 0 / техпоражение
  └──────────────── newMatch (хост) ◀────────── finished ◀──────┘
```

- **lobby.** Игроки входят и выходят, жмут «готов». Хост комнаты меняет настройки и жмёт «старт» (нужно минимум 2 игрока). Дуэль стартует, когда оба готовы.
- **loading.** Объект одним заходом читает из D1 фильмы и кадры матча (§8) и замораживает их в состоянии. Если подходящих тайтлов меньше, чем нужно, длина матча = числу найденных (минимум 1). Если не нашлось ни одного — ошибка `pool_empty`, комната возвращается в lobby.
- **ready(k).** Всем отправлен `prepare` с кадрами фильма k. Клиент качает все кадры и запасные и шлёт `ready`. Если какой-то кадр не загрузился (404), клиент шлёт `frameBroken`, сервер у всех заменяет его запасным и снова шлёт `prepare`. Переход в countdown происходит, когда готовы все в сети, или через `pvpReadyTimeoutSec` (30 с). Кто не успел: в комнате пропускает этот фильм (статус `out`), в дуэли играет, но его время уже идёт. Для k ≥ 2 фаза ready идёт одновременно с разбором фильма k−1: `prepare` уходит вместе с `reveal`, а таймаут отсчитывается от конца разбора.
- **countdown.** Сервер шлёт `countdown {startsInMs: 3000}` и запоминает `startedAt = now + 3000`. Клиент показывает кадр через `startsInMs` после получения. Отдельного сообщения «старт» нет.
- **playing.** Каждый идёт по кадрам сам: неверный ответ или пропуск открывает следующий кадр. После первого верного ответа дедлайн всех = `min(дедлайн, now + pvpAfterFirstCorrectSec)`. Фильм кончается, когда все участники угадали или исчерпали кадры, либо по дедлайну.
- **reveal(k).** Всем: ответ (название, год, постер, `mediaKey`), результаты фильма, таблица. В дуэли ещё урон и HP. Длится `pvpRevealSec` (8 с).
- **finished.** `finished` с итогами и всеми фильмами (каждый с полным набором кадров). Комната остаётся жить для «Новый матч» (хост комнаты; в дуэли — оба нажали «ещё»). До уборки итог лежит и в снапшоте, поэтому если приложение упало на финале, после переподключения итог вернётся. Клиент сохраняет итог у себя, когда получает, и шеринг работает от этой копии. Если игрок не вернулся до уборки, итог пропадает. Это принятый риск: история на сервере не хранится.
- **Уборка.** Если в комнате 10 минут (`pvpIdleCleanupSec`) нет ни одного игрока в сети, объект делает `deleteAll()` и исчезает, а код освобождается. То же происходит через 10 минут после `finished`, если никто не начал новый матч.

### Пауза (только комната, только хост)

- Пауза возможна в ready, countdown, playing и reveal. Сервер запоминает, сколько осталось до текущего срока, и снимает его. Всем приходит `paused`, клиенты закрывают кадр оверлеем. Ответы на паузе отклоняются (`error paused`).
- `resume`: снова 3-2-1 (`resumed {startsInMs}`), затем отсчёт продолжается с остатка. Время паузы вместе с этими 3 с в очки не идёт (§5).
- Через `pvpPauseMaxSec` (300 с) пауза снимается сама.

### Хост (только комната)

- Хост — создатель комнаты.
- Если хост ушёл (`leave`), хостом сразу становится следующий по времени входа из тех, кто в сети.
- Если хост пропал из сети, передача происходит через `pvpHostGraceSec` (30 с). Вернувшийся хост роль назад не получает.
- Если в сети никого, хост остаётся прежним до первого вернувшегося.

### Вход, выход, возврат

- **Место игрока** — запись по uid. Её убирает только `leave` в лобби или кик.
- **Комната.** Вход возможен в любой фазе, если есть место (`pvpRoomMaxPlayers` = 8). Вошедший или вернувшийся посреди фильма, который в этом фильме не участвовал, сидит до следующего фильма (`out`). Кадров текущего фильма он не получает, видит только прогресс остальных.
- **Вернулся в свой фильм.** Если игрок участвовал в текущем фильме и вернулся до его конца, он продолжает с того же кадра. Время шло, пока его не было. Это работает и в комнате, и в дуэли.
- **`leave` во время матча.** В комнате игрок остаётся в таблице как «вышел» и может вернуться по коду на своё место. В дуэли `leave` — это сразу техническое поражение.
- **Дуэль, обрыв.** Если игрок не в сети или свернул приложение `pvpDuelForfeitSec` (60) секунд подряд, засчитывается техническое поражение, как в шахматах. Если сроки истекли у обоих — ничья (`abandoned`). Пока идёт отсчёт, у отсутствующего в `Player` есть `forfeitInMs`, и клиент показывает сопернику обратный отсчёт. Время «свернул» в лобби не считается: отсчёт начинается со старта матча.

### Кик и скрытие ника (хост комнаты, в любой фазе, включая паузу и финал)

- **`kick {uid}`.** Сокет игрока закрывается с кодом `4003`, uid попадает в список изгнанных, вернуться по тикету нельзя (`kicked`). Его очки и строки исчезают из таблицы и итогов, всем уходит `playerRemoved`. Кикнуть можно и того, кто уже вышел.
- **`hideName {uid}`.** До конца жизни комнаты ник игрока у всех заменяется его `alias` (§10), всем уходит `player` с новым именем.
- **Скрыть ник только для себя** — функция клиента. Сервер уже присылает `alias` каждого игрока.

## 5. Очки, время, HP

**Время ответа** — `t = пришло − startedAt − паузы внутри фильма`. Сервер ставит отметку в момент получения сообщения. Время, присланное клиентом, не читается: его можно подделать («ответил за 0.3 с»). Пинг одного игрока примерно постоянный, и задержка в несколько сотен миллисекунд — это меньше одного очка.

**Очки за фильм:**

```
угадал на кадре k:  base[k] + round(pvpTimeBonusMax × max(0, 1 − t / timeLimit))
не угадал:          0
base = pvpFrameBase = 900, 750, 600, 450, 300, 150      pvpTimeBonusMax = 100
```

`timeLimit` здесь — исходный лимит фильма, а не урезанный после первого верного ответа. Бонус (≤ 100) меньше разрыва между соседними кадрами (≥ 150), поэтому любой ответ на кадре k дороже любого ответа на кадре k+1. Пролистать кадры, чтобы ответить быстро, невыгодно. Неверная догадка стоит столько же, сколько пропуск, поэтому угадывать наугад выгоднее, чем пропускать. Если поднять `pvpTimeBonusMax` выше 150, быстрый ответ на следующем кадре сможет обогнать медленный на предыдущем.

При сложности 4 или 3 кадра раунд — это первые 4 или 3 кадра обычной раскладки, самые трудные. Веса `base[1..4]` или `base[1..3]` те же.

**Комната.** Сумма очков, места по убыванию, одинаковые суммы делят место.

**Дуэль.**

```
урон отстающему = (очки лидера − очки отстающего) × mult(i)
mult(i) = 1,  если i < pvpDuelMultiplierFrom (4)
        = 1 + pvpDuelMultiplierStep (0.5) × (i − pvpDuelMultiplierFrom + 1)   →  ×1.5 на 4-м, ×2 на 5-м …
HP = pvpDuelHP (3000)
```

Множитель повышает цену фильма, а не награждает лидера. Если оба не угадали, урон 0. Если HP ≤ 0, матч кончается. Если фильмы кончились (`pvpDuelMaxFilms` = 20 или пул меньше), побеждает тот, у кого больше HP; при равных HP — ничья. За один фильм проиграть нельзя: максимум при ×1 — 1000.

## 6. Протокол WebSocket

JSON-объекты с полем `t`. Номер `seq` — счётчик состояния комнаты: растёт на 1 за каждый шаг комнаты, который что-то изменил для игроков, и стоит на каждом сообщении сервера (кроме `pong`). Несколько сообщений одного шага (например, `reveal` и `prepare`) идут с одним `seq`. Клиент запоминает наибольший виденный `seq` (его он отдаёт в `lastSeq`) и отбрасывает сообщения с `seq` меньше, чем у последнего применённого снапшота.

### Клиент → сервер

| `t` | Поля | Кто, когда |
|---|---|---|
| `ping` | — | все, раз в 10 с (автоответ `pong`) |
| `ready` | `film` | все: lobby (`film` = 0) и ready(k) |
| `unready` | — | lobby |
| `guess` | `film, frame, tmdbId, mediaType` | участник в playing; `frame` — номер кадра, который он видит |
| `skip` | `film, frame` | участник в playing; пустой ответ — тоже `skip` |
| `frameBroken` | `film, index` | ready(k): кадр не загрузился |
| `away` | `away: bool` | свернул или развернул приложение |
| `leave` | — | все |
| `settings` | `films?, frames?, timeLimitSec?` | хост комнаты, lobby |
| `start` | — | хост комнаты, lobby |
| `pause` / `resume` | — | хост комнаты |
| `kick` | `uid` | хост комнаты |
| `hideName` | `uid` | хост комнаты |
| `newMatch` | — | хост комнаты, или оба в дуэли; только finished |

Если `guess` или `skip` пришли с неверным `film` или `frame` (повтор после обрыва или двойное нажатие), они игнорируются, и игроку уходит `snapshot`. Так сообщения идемпотентны.

### Сервер → клиент

| `t` | Поля | Кому |
|---|---|---|
| `welcome` | `you {uid, resumeToken}, seq` + `snapshot`, если `lastSeq` ≠ `seq` | подключившемуся |
| `snapshot` | всё состояние глазами этого игрока (ниже) | лично |
| `player` | `Player` | всем: вход, изменение готовности, сети, ника, хоста |
| `playerRemoved` | `uid, reason: "left"\|"kicked"` | всем |
| `settings` | `Settings` | всем |
| `loading` | — | всем |
| `prepare` | `film, total, frames: [Frame], spares: [Frame]` | участникам фильма |
| `countdown` | `film, startsInMs, timeLimitMs` | всем |
| `progress` | `uid, film, frame, status` | всем: `thinking`, `solved`, `failed`, `out` |
| `guessResult` | `film, frame, correct` | лично |
| `deadline` | `film, endsInMs` | всем, после первого верного ответа |
| `paused` | `remainingMs, autoResumeInMs` | всем |
| `resumed` | `startsInMs` | всем |
| `reveal` | `film, answer: Answer, results: [FilmResult], standings: [Standing], duel?: {multiplier, damage: {uid: n}, hp: {uid: n}}, nextInMs` | всем |
| `finished` | `reason, standings, films: [{film, answer, frames: [Frame], results}]` | всем |
| `error` | `code, message` | лично |

`reason` в `finished` бывает `films_done`, `knockout`, `forfeit`, `abandoned` или `draw`.

Типы:

```
Player     {uid, name, alias, icon, color, isHost, ready, connection: "online"|"away"|"offline", left, joinedAt, forfeitInMs?}
                                                                     (forfeitInMs — только дуэль, только пока игрок away/offline во время матча)
Settings   {kind, mediaType, films, frames, timeLimitSec, maxPlayers} (+ для дуэли: hp, maxFilms; maxPlayers в комнате — pvpRoomMaxPlayers, в дуэли 2)
Frame      {path, width, height}                                     (file_path TMDB, без названия)
Answer     {mediaKey, tmdbId, mediaType, title, originalTitle, year, posterPath}
FilmResult {uid, solvedAtFrame|null, ms|null, points}
Standing   {uid, place, total}                                       (дуэль: {uid, hp})
```

`snapshot`:

```
{seq, phase, code, you: uid, hostUid, settings, players: [Player],
 film: {index, total, phase, frames?: [Frame], spares?: [Frame], yourFrame?, yourStatus?,
        progress: [{uid, frame, status}], endsInMs?, startsInMs?},
 paused?: {remainingMs, autoResumeInMs},
 standings, duel?: {hp, multiplier},
 lastReveal?, finished?}
```

`frames` есть в снапшоте только у участника текущего фильма. Своё правильное название клиент берёт из своей подсказки. Сервер не шлёт название никому до `reveal`.

**Чего соперник не видит:** текст или id чужого ответа. **Что видит:** номер кадра (каждое увеличение означает «ошибся или пропустил»), статус, сеть. Очки и места видны только на `reveal`, HP в дуэли — всегда.

## 7. Обрывы и переподключение

1. **Сокет закрылся или замолчал на 30 с** — игрок `offline`, всем уходит `player`. Таймер фильма не останавливается.
2. **Клиент сразу переподключается**: `GET /ws?lastSeq=<n>` с `Authorization: PvP <resumeToken>`. Объект отвечает `welcome`. Если `lastSeq` < текущего, к нему прикладывается `snapshot`, из которого клиент перерисовывает экран целиком. Журнал сообщений не хранится: снимок проще и надёжнее досылки.
3. **Переподключение не удаётся** (DPI режет сокеты) — после двух неудач подряд клиент переходит на `POST /poll` раз в 2 с с тем же resume-токеном. В `send` идут те же сообщения клиента, в ответе — `snapshot`, если `seq` вырос, и личные сообщения (`guessResult`, `error`) с последнего опроса. Сообщение клиента (`guess`, `skip` и любое другое) уходит отдельным `POST /poll` **сразу**, не дожидаясь очередного опроса: время ответа сервер засекает по приходу, и ответ не должен лежать в телефоне до 2 с. Игрок на опросе считается `online`, если опрашивал не дольше 10 с назад. Каждые 30 с клиент пробует вернуться на сокет.
4. **Комната умерла** (уборка) — `room_not_found`, клиент выходит в меню.

### Лимит на поток сообщений

Каждое входящее сообщение сокета будит объект и тратит общий суточный бюджет аккаунта, поэтому у каждого сокета есть ведро:
- **30 сообщений сразу, дальше по одному каждые 2 с.** Состояние ведра лежит во вложении сокета, хранилище не пишется. Ping отвечает рантайм, в ведро он не попадает. Живому игроку нужно несколько сообщений на фильм.
- **Переполнение или сообщение длиннее 4096 символов** закрывают сокет с кодом `4029`. Клиент может переподключиться по resume-токену.
- **Третье переполнение** (`FLOOD_STRIKES`) — игрок исключён из комнаты, как при кике (`playerRemoved {reason: "flood"}`), resume-токен и тикеты больше не работают. В дуэли во время матча это техническое поражение.
- **Подключение и опрос** (`ws`, `poll`) не проходят через `authenticate`. Оба токена подписаны (`pvp1.` — тикет, `pvpr1.` — resume-токен, HMAC от `JWT_SECRET` с разными префиксами), поэтому воркер проверяет подпись и код комнаты сам и отказывает поддельным (`401 token_invalid`), не будя объект. Затем запрос проходит `REQUEST_LIMITER` с ключом «код комнаты + uid из токена»: новым фальшивым токеном свежий лимит не получить. Ключ не по IP, потому что друзья за одним VPN-выходом делили бы один лимит. Объект дополнительно сверяет resume-токен с выданным — так кик и бан за флуд его отзывают.

**Коды закрытия сокета:**

| Код | Причина | Что делает клиент |
|---|---|---|
| `4000` | `left` — игрок сам вышел | ничего |
| `4001` | `replaced` — открыт другой сокет этого игрока | ничего: работает новый |
| `4003` | `kicked` — кик хоста | выйти в меню, не переподключаться |
| `4004` | `room_closed` — комната убрана | выйти в меню |
| `4008` | `stale` — сокет молчал 30 с | переподключиться по resume-токену |
| `4029` | `too_many_messages` | переподключиться; очередь не сбрасывать разом (ниже) |
| `4030` | `removed_for_flooding` — третий раз | выйти в меню, не переподключаться |
| прочие, обрыв сети | — | переподключиться по resume-токену |

**Клиент сам не должен упираться в лимит.** Исходящие сообщения идут через очередь с тем же ведром, но меньше серверного: например, 20 сразу и одно раз в 2 с. Средний темп — не чаще одного сообщения в 2 с, а не раз в секунду: при отправке раз в секунду серверное ведро кончится примерно за минуту. После переподключения ведро у нового сокета снова полное, но счётчик переполнений привязан к игроку, поэтому неотправленное досылается через ту же очередь, а не пачкой. Ping (`{"t":"ping"}` раз в 10 с) в очередь не попадает: его отвечает рантайм, и в ведро он не считается.

## 8. Выбор фильмов и кадров

При переходе в `loading` объект делает 2 запроса к D1:

1. Ключи: `buildCatalogQuery({mediaType, minApprovedImages: frames}, {excludeDailyFrom: today})` с обходом по `idx_media_shuffle` от случайной точки, как в `pickRandomKey`. Читается `3 × N + сыгранные` ключей подряд (с переходом через начало, не больше 90). Из них:
   - сначала случайно берутся те, которых в этой комнате ещё не было;
   - если их меньше N, недостающие добираются из сыгранных: комната помнит, когда играла каждый тайтл, сыгранные сортируются от давних к недавним, берётся давняя половина (с округлением вверх) и из неё случайно — сколько не хватает. Если и этого мало, добирается из второй половины. Так последние фильмы прошлого матча не повторяются сразу, а порядок не становится предсказуемым;
   - если тайтлов в пуле меньше N, длина матча = размеру пула (минимум 1).
2. Тайтлы и кадры: `media_items` и `media_images` по `key IN (…)` (одобренные, не пропавшие). Для каждого тайтла `selectRoundFrames(images, frames, {random})` и `selectSpareFrames(…, 3, {random})` с `seededRandom(hashString(code + matchNo))`. Если у тайтла играбельных кадров меньше `frames`, он выбрасывается.

Раскладка, ответы и пути кадров замораживаются в состоянии объекта. Если куратор поменяет кадры посреди матча, матч этого не заметит. Пропавший с TMDB кадр заменяется запасным по `frameBroken` у всех одинаково.

Ответ верный, если `tmdbId === film.tmdbId && mediaType === film.mediaType`. Ремейки и тёзки различаются по id.

## 10. Ник и аватар

- **Ник:** только латиница, `[A-Za-z0-9_]{3,16}`. Кириллицу и другие алфавиты не принимаем: с похожими буквами (латинская `x` и кириллическая `х`) и смешением алфавитов фильтр не справится, а эмодзи, невидимые символы и переворот направления текста ломают таблички с именами. Кириллицу можно добавить позже отдельным алфавитом, без смешения в одном нике и со своим стоп-листом. Фильтр: нижний регистр, замена похожих символов (`0→o 1→i 3→e 4→a 5→s 7→t`), подчёркивания убираются, подстроки сверяются со стоп-листом (английский мат и русский латиницей). При отказе — `400 name_rejected`.
- **Генератор:** прилагательное + существительное из киножаргона, CamelCase, ≤ 16 символов, слова без товарных знаков: `NoirGaffer`, `SilentFoley`, `MidnightReel`. Около 40 × 40 слов. Ник по умолчанию — `generate(hash(uid))`, `alias` — `generate(hash(uid + ":alias"))`. Оба вычисляются и не хранятся.
- **Одинаковые ники в одной комнате** — у второго `_2`, у третьего `_3`. Ник обрезается, чтобы с суффиксом уложиться в 16 символов: `MidnightProjecti` → `MidnightProjec_2`.
- **Аватар:** `icon` и `color` — слаги из серверных списков. Сами списки выберем позже, сейчас в коде заглушки по 12 иконок и 10 цветов.
- **Хранение:** строка в `pvp_profiles` появляется только при первом `PATCH`. До этого всё вычисляется.

## 11. Схема D1

```sql
CREATE TABLE IF NOT EXISTS pvp_profiles (
    uid        TEXT PRIMARY KEY REFERENCES users(uid) ON DELETE CASCADE,
    name       TEXT,                                -- NULL: сгенерированный по uid
    name_seed  INTEGER NOT NULL DEFAULT 0,          -- 🎲: сдвигает генератор
    icon       TEXT,
    color      TEXT,
    updated_at INTEGER NOT NULL
);
```

Больше таблиц нет: комнаты живут в объектах, история не хранится. Удаление аккаунта убирает профиль каскадом, `lib/accounts.js` не меняется. Миграция — `docs/pvp-migration.sql`, тот же `CREATE TABLE`.

## 12. Стоимость (Free, сверено с документацией 30.10.2026)

Лимиты:
- **Workers:** 100 000 запросов в сутки.
- **DO:**
  - 100 000 запросов в сутки (HTTP, alarm и входящие сообщения сокета по курсу 20:1; исходящие и ping бесплатны);
  - 13 000 ГБ·с в сутки, при 128 МБ на объект это ≈ 28 часов бодрствования;
  - 100 000 записанных строк в сутки, `setAlarm` = 1 строка.
- **D1:** 50 запросов на вызов, 100 000 записей в сутки.
- Сброс всех лимитов в 00:00 UTC (03:00 МСК).

Замерено ботами через шим (`tools/pvp-bots.mjs --local`, счётчики объекта):

| На матч | Дуэль, ~10 фильмов | Комната 8 × 10 |
|---|---|---|
| Запросы к воркеру | 4–5 (создать, тикет, 2 апгрейда) | 16–17 |
| Сообщения сокета → запросы к DO | ~60 → 3–4 | ~225 → 12 |
| Alarm | ~10 | ~9–12 |
| Запросы к DO всего | **~18** | **~38** |
| Записи хранилища DO (`put` + `setAlarm`) | ~110 | ~280 |
| Длительность DO, оценка для людей (~8–10 мин) | ~60–75 ГБ·с | то же |
| Запросы к D1 | 4 при старте матча (только чтения) | то же |
| Записи D1 | **0** | **0** |
| **Матчей в сутки (узкое место — длительность)** | **~170–215** | **~170–215** |

Расход за сегодня виден в `GET /v1/admin/usage`, блок `durableObjects`:
- **`requests`** — из `durableObjectsInvocationsAdaptiveGroups`. Входящие сообщения сокета с Hibernation там считаются один к одному, а оплачиваются как 20:1, поэтому цифра завышена: это безопасная сторона для лимита.
- **`gbSeconds`** — `activeTime` из `durableObjectsPeriodicGroups` × 0.125 ГБ.
- **`rowsWritten`** — из того же набора.

Каждое число запрашивается отдельным запросом. `activeTime` и `rowsWritten` нет в опубликованных примерах Cloudflare: если какое-то поле не существует, вместо числа придёт `null`, а причина — в `unavailable`. Пределы — в `limits.durableObjects`.

По запросам и записям хранилища запас в сотни матчей в сутки. Длительность — по-прежнему оценка: шим её не меряет. Боты отвечают быстрее людей (их 10 фильмов прошли за 4 виртуальные минуты), поэтому для людей взято 8–10 минут.

Длительность считается на объект, а не на игрока. Если её не хватит, есть тариф Paid ($5): 400 000 ГБ·с в месяц.

На опросе (§7) каждый игрок тратит 30 запросов к воркеру и 30 к DO в минуту. Это аварийный режим, а не основной.

## 14. Не входит и принятые риски

Не входит: открытые комнаты, пароли, очередь, рейтинг, история матчей, режим «выбери из вариантов», жалобы на кадр внутри PvP (кнопку клиент прячет), MultipeerConnectivity, кнопка «передать хоста».

**Принятый риск: код комнаты можно подобрать.** Кодов 10⁶. Вход по коду (`POST /rooms/{code}/ticket`) требует access-токен и проходит `REQUEST_LIMITER` — 120 запросов в минуту на аккаунт. Если живых комнат N, одна попытка попадает с вероятностью N / 10⁶:

| Живых комнат | Один аккаунт, 120/мин | 600 аккаунтов (час регистраций с одного IP при `AUTH_LIMITER` 10/мин) |
|---|---|---|
| 10 | 1 попадание за ~14 ч | ~1 за 1.4 мин |
| 100 | 1 за ~1.4 ч | ~7 в минуту |
| 1000 | 1 за ~8 мин | ~70 в минуту |

Анонимный аккаунт заводится бесплатно, поэтому лимит на аккаунт сдерживает только одиночку; серьёзный подборщик упирается раньше в суточный бюджет запросов Free (каждая попытка — запрос воркера и пробуждение объекта), то есть это скорее риск расхода квоты, чем взлома. Цена попадания низкая: чужой оказывается в комнате друзей и виден в списке, хост его кикает; в идущую дуэль не войти (`match_running`). При нынешнем масштабе (единицы–десятки комнат одновременно) 6 цифр приемлемы. Если комнат станут сотни, дешевле всего: отдельный лимит на `ticket` для кодов без комнаты (например, 10 промахов в минуту на аккаунт) — он режет и подбор, и пробуждение пустых объектов; удлинение до 8 цифр уменьшает шанс в 100 раз и оставляет цифровую клавиатуру.

**Принятый риск: ответ можно узнать скриптом.** Фильм и кадры выбирает сервер, но чтобы показать кадр, клиент должен его скачать, и для этого получает TMDB `file_path`. Публичный индекс каталога отдаёт ключи всех опубликованных тайтлов (`movie_10483` = id в TMDB), а список кадров фильма по id выдаёт открытый API TMDB. Скрипт заранее собирает кадры всех 31 фильма, видит путь кадра в трафике и знает ответ раньше отсчёта.

- **Комнаты друзей:** принимаем. Против такого игрока есть кик.
- **Скрывать путь не будем:** прокси кадров через воркер — это ~700 запросов на матч вместо ~17, а скрипт следующего уровня сравнивает уже сами картинки по перцептивному хэшу.
- **Для будущего рейтинга понадобятся** кадры, изменённые заранее (обрезка и масштаб, копии в R2), чтобы перестал совпадать и путь, и хэш; пул в сотни тайтлов; поиск неправдоподобных результатов (например, стабильно «1-й кадр за 1 с»). Полностью закрыть это нельзя, можно только сделать дорогим и заметным.

## 16. Клиент: что проверено

Клиент — `Franamed/PvP/` (контракты, транспорт, состояние матча, сессия, фикстуры) и `Franamed/Backend/Services/BackendPvPService.swift`. Тесты — SwiftPM-пакет `Tools/PvPKit` (`swift test`), фейковый сервер — настоящий воркер на localhost (`Tools/PvPKit/Server/pvp-server.mjs`).

- **macOS, настоящий `URLSessionWebSocketTask`:** все 10 тестов транспорта проходят — `Authorization: PvP …` в заголовке апгрейда, ping, resume, переход на опрос и обратно, коды закрытия 4000/4001/4003/4004/4029/4030, `401 token_invalid` на поддельный тикет.
- **Linux:** FoundationNetworking в тулчейне собран с libcurl без WebSocket, поэтому сокет там подменяется POSIX-клиентом из `Tools/PvPKit/Shims`; остальной код тот же.
- **`wrangler dev`:** Swift-клиент (HTTP, транспорт, сессия) против ботов, комната и дуэль, с обрывом посреди матча — `PVP_WRANGLER_URL=http://127.0.0.1:8787 swift test --filter WranglerTests`.
